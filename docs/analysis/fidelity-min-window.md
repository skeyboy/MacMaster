# P4 最小窗口核对（fidelity-min-window）

> 证据：`docs/verification/p4-min-window/`。`900-requested-*` 是修前（下限 900pt），
> `min-*` 是修后（下限 1000pt）。两批都是 `MM_APPEARANCE=light`、零合成点击。

## 0. 结论先行

1. **应用自己的窗口下限违反了设计稿的地板值。** `tokens.css` 里 `.content { min-width: var(--content-min) }`
   = **760pt**，侧栏实测 220pt，所以窗口要到 **980pt** 以上内容区才不低于稿定的值；
   实现写的是 `minWidth: 900`，内容区只剩 **670pt**，比稿少 90pt。
   所有"窄窗溢出"都是这一个数引起的。
2. 后果最重的是**磁盘分析页头部**：分段控件 + 132pt 筛选框 + 两个按钮，在 670pt 内容区里放不下，
   AppKit 选择压缩按钮而不是截副标题，于是标题被截成 **"重新…"** 和 **"选择…"**——
   用户看不出这两个按钮是干什么的。这不是"窄一点就少显示点"的降级，是主操作不可读。
3. 修法是把下限抬到 **1000×600**（`MacMasterApp.swift`），一行。改后同一批截图里
   磁盘页头部三件控件标题完整、概览页的"总占用 · 10 核 / 4 性能 + 6 能效"也不再被截。
   没有给头部加"窄档隐藏筛选框"的降级逻辑——稿子只画了宽档，先按稿的地板值收口，
   真要做窄档得先补一张窄档 artboard（见 §4）。
4. 顺带修掉一个**假证据**：`MM_WINDOW_SIZE` 的日志回显的是"请求值"，
   而窗口被下限夹住后的实际尺寸要到下一轮布局才稳定。实测同一轮里日志写"实际 900x600"、
   截图却是 2000px（=1000pt）宽。现在日志写"请求 X，窗口实际 Y（被夹住）"。

## 1. 方法与量到的数

```zsh
./Scripts/p4-sweep.sh /tmp/mmapp-p5/MacMaster.app /tmp/p4-min5 light 900x600
```

- 请求 900×600 是**故意的**：它低于修后的下限，用来验证"用户把窗口拖到多小都不会出现截字"——
  夹取由 AppKit 做，不需要每个页面自己判断。
- 窗口真实尺寸用截图反查，不信日志：`sips -g pixelWidth`，@2x 下 2000px = 1000pt。
  修前两批都是 1800×1304px（900×652pt），修后 8 屏全部 2000×1304px。
- 逐屏看的是三件事：**控件标题有没有被截**、**有没有重叠**、**有没有横向溢出/出现横向滚动条**。
  纵向溢出算正常（页面本来就该滚），只有设置 sheet 这种固定块要单独看。

## 2. 逐屏结果

| 屏 | 修前（内容区 670pt） | 修后（内容区 771pt） |
| --- | --- | --- |
| 概览 | 仪表副文案截成"总占用 · 1…"/"4 性能 + 6…"，内存构成行中段截 | **完整**；只剩"交换 6.36 GB / 7.52…"一处尾截（同一行的第二个数，上面已有总量） |
| 系统清理 | 副标题中段截成"已扫描 16 类 · 可释…2026-10-01 14:41"，**可释放量被吃掉**；控件完整 | 控件与副标题完整；这轮正好抓到扫描中骨架态，进度行"已处理 1,818 项 · ~/Library/Containers/…"未截 |
| 应用卸载 | 未见截字 | 未见截字 |
| 磁盘分析 | **按钮标题截成"重新…""选择…"**，副标题截成"选择一…开始分析" | **三件控件标题全部完整**，副标题完整；带结果态另测，见 §3 第三条 |
| 系统监控 | 4 个指标卡 + 每核列表正常滚动，无溢出 | 同上，无变化 |
| 隐私守护 | 无截字（口径行本来就长，靠换行） | 无截字 |
| 系统优化 | 未见截字 | 未见截字 |
| 设置 sheet | 高度不足时走内部滚动，未裁切 | 同左，滚动条可见 |

**重叠**：8 屏两档都没发现元素叠在一起。
**横向滚动条**：没有出现——被压缩的是文字，不是布局，所以溢出是以"截字"的形式暴露的，
这也正是它容易被漏掉的原因：窗口不报错，只是话说不完。

## 3. 归属

- **实现该改（已改）**：`MacMasterApp.swift` 的 `.frame(minWidth: 900 → 1000, minHeight: 600)`，
  注释里写清推导（稿 760pt 内容地板 + 侧栏 220pt），免得下一个人当成拍脑袋的数字又改回去。
- **实现该改（已改）**：`LaunchBehavior.swift` 的尺寸凭据改为回读夹取后的真实窗口尺寸。
- **实现该改（已改，补测才暴露）**：磁盘页副标题的**字段顺序**。抬到 1000pt 后控件不再截了，
  但"带扫描结果"的磁盘页在 1000pt 下副标题仍被中间截断，而且被吃掉的是**占用总量**
  （`77.8 MB`）——因为路径占着开头。改成按"谁该活下来"排序（占用 · 文件数 · 用时 · 路径）后，
  实测截成 `77.8 MB · 44…aster-disk-fixture`：占用和目录名保住，代价是没掉"用时"和"个文件"字样。
  证据：`min-disk-scanned-before-reorder.jpg`（改前）/ `min-disk-scanned.jpg`（改后）。
- **没改的一条**：Treemap 图例行尾"面积 = 实际磁盘占用（st_blo…"在 1000pt 下也会截掉后半句
  （"双击下钻 · ⌘ 点击标记"）。这是提示不是数据，且下钻/标记在详情面板里有按钮，
  所以先记着不动；要动就该连着图例一起重排，不是三行能收口的。
- **稿该补**：`--content-min: 760px` 只写在 CSS 里，`README` 和稿子都没有"窄窗档"的 artboard。
  现在实现的行为是"不许比 760 更窄"，而不是"更窄时长这样"。如果将来要支持更小的窗口
  （分屏 1/3 大约就是这个宽度），得先出窄档稿：头部控件如何降级、哪些文案优先保留。

## 4. 没能验证到的部分

- **只测了浅色档**。深色档在 1000pt 下没拍——本轮改动只影响宽度，色档不受影响，
  但"没拍"和"没问题"是两件事。
- **中文以外的语言**：English 下按钮标题更长（"Rescan" / "Choose Folder"），
  900pt 时的截字只会更早出现。没有拍英文档的最小窗口。
- **辅助功能大字号**：Dynamic Type 放大后同样的宽度能装的字更少，未测。
- **磁盘页"有结果"态**：补测了（`min-disk-scanned*.jpg`），并因此改了一次副标题字段顺序，见 §3。
  但真机用户目录（带 FDA 权限、受保护项不止 `Library` 一个）下的窄窗没测——
  徽标那行会列出更多名字，宽度余量没量过。
- **侧栏收起态**：`⌘.` / 工具栏那个收起按钮没点过（禁止合成点击），
  收起后内容区变宽，理论上更安全，但没证据。

## 5. 提请协调者

1. `--content-min: 760px` 现在是**只有稿知道、实现不知道**的约束（实现侧此前是 900）。
   建议在 `docs/design-system/README.md` 里把它写成一条明面红线：窗口下限 = content-min + 侧栏宽。
2. 若产品要支持"更窄的窗口"（分屏、13 寸外接），需要一张窄档 artboard 定义头部降级顺序，
   否则会重演本轮：各页自己决定截哪句话，8 屏截出 8 种规则。
