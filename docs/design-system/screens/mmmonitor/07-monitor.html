E 温度与风扇（E1 是真机读数、E2–E5 是夹具态， 五档全部有实机照片：见 docs/verification/p64/ 与暗档 p64-dark/）。 这张卡 2026-10-04 才存在，A/B/C/D 四稿画它是"实现独有、稿没画"的状态，本稿补上。 它排在整页最后（进程卡之后），760pt 窗口里永远在折叠线以下，所以取证走新钩子 MM_MONITOR_CARDS=sensors（只渲染要拍的那张卡，手法照 MM_GUARDIAN_CARDS）， 不靠把窗口画高碰运气；相邻与卡间距另有 MM_MONITOR_CARDS=process,sensors 一张（照片 07）。 数据来源是本机 AppleSMC 的用户客户端，只读：整个实现只发三条命令 （readKeyInfo 9 / readBytes 5 / keyFromIndex 8）， 写命令与 F{id}Md、Ftst 这类解锁风扇控制的路径在结构上就没接进来—— 写 SMC 能把风扇永久锁死，注释里反对一次不够，得让它发不出去。 本机实测事实（Scripts/smc-probe.swift，2026-10-04）：键表 #KEY=1369， 其中 T* 180 个；174 个是 flt （小端 IEEE float，能解）， 6 个是 ioft（8 字节、语义没公开、恒为 0）——刻意不支持， 把"读不懂"塌成 0 °C 就是虚报。风扇 FNum=1、F0Ac=1000、F0Mn=1000、 F0Mx=4900、F0Tg=1000。这条把路线图里"本机 Mac mini 无风扇、价值最低"那句判错了： 本机有 1 台风扇且四个值全可读。整表 174 键扫一遍 ≈22–25 ms（两次往返与缓存类型无实测差别，故不设缓存）， 键名枚举 1369 次往返 ≈150 ms、只有首帧付；采样跑在已有的 detached 后台任务上，不压主线程。 174 个键怎么摆：按键值降序、同值按键名升序（确定性排序，不是随机前 8），只露最高的 8 行， 其余用一行 caption 交代总数；键名一律用 SMC 原文，不编 CPU/GPU 归属——苹果没公布键位对应哪块硬件， 标成"CPU 温度"是猜。E1 那张里 TCMz / Tp0f / Tp3X 同为 88.3 °C 而顺序如此， 正是同值按键名升序那条规则的照片证据。 转红阈值 90 °C 是我们自定的，SMC 不告诉你"这个键算不算热"，取的是距 Apple Silicon 节流点的经验余量， 不是苹果官方阈值；空闲时本机最高 54.5 °C，所以红档只能靠夹具（E5）。 进 90 / 出 85 两个阈值，不是一个：本机截图负载下实测最高 89.4 °C，离单点阈值只差 0.6 °C， 而采样每 2 秒一帧——单点判定时同一行的颜色会在 89.x↔90.x 之间闪。改动只在"什么时候复原"， 90 这个坎没挪（把阈值抬到 95 只是把判据搬到测量够不着的地方，不算修）。 风扇一句与"风扇 0 台"是两句话：fanCount == nil（FNum 没读到）画 E4 那两行， fanCount == 0 画 E3 那句；未知不许画成 0 台。 顺带一个观察（不是结论）：两次采样（空闲 54.5 °C 与截图负载下 89.4 °C）F0Ac 都是 1000 = F0Mn， 连 F0Tg 也是 1000——这台机器的 SMC 目标转速就贴在最低档。我们只报读到的数，不解释政策。 对应实机视图：MonitorView.sensorsCard（MMMonitor.swift）； 纯函数与解码在 Sensors.swift / SMC.swift / SensorSampler.swift。
